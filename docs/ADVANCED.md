# Техническая архитектура симулятора

## Поток обработки

`JSON / CLI → Pydantic-валидация → точный перебор мер → фиксированный Score → 3 профильных агента → оркестратор → проверка чисел → JSON / текст`.

`akim_sim/dataset.py` содержит 5 районов, 10 показателей, веса, доли населения и M1–M14. `model.py` реализует формулу, лаги, синергии, клиппинг и семь правил набора. `optimizer.py` перебирает допустимые размещения мер и применяет необязательные верхние лимиты сфер. `engine.py` формирует метрики, сравнение с общим оптимумом и объяснимый результат; `risk.py` вычисляет явно отмеченные прокси. `agents.py`, `llm.py`, `pipeline.py`, `guardrails.py` формируют объяснение без права изменять Score. `api.py` — стандартная библиотека Python, без дополнительного веб-фреймворка.

## Математическая модель

Для района d и показателя k:

```text
I′[d,k] = clip(I[d,k] + Σ_{m действует в d} e[m,k] · (8−L[m])/8 + S[d,k], 0, 100)
D[d] = Σ_k w[k] I′[d,k]
D_avg = Σ_d p[d] D[d]
N_crit = Σ_{d,k} 1[I′[d,k] < 40]
Score = clip(0.7 D_avg + 0.3 min_d D[d] − N_crit, 0, 100)
```

`p = {Есиль: .27, Алматы: .24, Сарыарка: .20, Байконур: .13, Нура: .16}`. Веса по T1,T2,E1,E2,S1,S2,B1,B2,C1,C2: `.10,.10,.09,.11,.11,.11,.09,.09,.10,.10`. Бонусы синергий: M1+M2→T1+2 в районе M1; M10+M12→B1+2 в районе M10; M5+M6→E2+2 в районе M5. Бонус без умножения на лаг. Исходная база 52.558, эталонные пять мер 56.543, общий максимум при бюджете 100 — 57.237.

`allocation` означает ровно пять входных сумм `x[s] ≥ 0` и `Σ_s x[s] ≤ B`. Оптимизатор выбирает набор P с `|P| = 5`, `Σ_{m∈P, sector(m)=s} cost(m) ≤ x[s]` для каждой сферы, ограничением `≤2` мер на сферу, общим бюджетом, без повторов и несовместимых пар. Максимизируется **тот же Score(P)**, что в `measures`. При недопустимых лимитах Score не создаётся. Входные суммы — лимиты, фактические траты могут быть меньше. Отдельной функции `exp`, целевых долей сфер и искусственных штрафов тут нет. Эффект насыщается при выборе лучших мер и клиппинге показателей, но синергия может локально повышать предельную отдачу.

## Агенты и достоверность

Analytics объясняет рассчитанные числа. Urban Expert сопоставляет районные изменения с условиями города. Social & Risk описывает модельные прокси и вымышленные реакции, явно отделяя их от измерений. Chief Advisor получает три результата и строит доклад. Профильные роли работают параллельно, Chief Advisor — после них. Для LLM сначала применяется strict JSON Schema, затем JSON mode и один запрос исправления; сбой переводит конкретную роль на предсказуемый offline-отчёт. Проверка чисел связывает текст с полями движка и отмечает неподтверждённые значения. Живой вызов OpenAI без пользовательского ключа не был проверен; локальные моки проверяют сетевой контракт и деградацию.

Прокси риска — индексы 0–100 на игровых показателях, не статистически откалиброванные вероятности. Реакции жителей написаны как вымышленные сценарии; соцсети не подключаются. Ливни, мороз и рост населения в блоке чувствительности меняют веса показателей, не создают события.

## Вход и выход

```json
{"mode":"allocation","allocations":{"transport":25,"green":15,"social":25,"safety":15,"utilities":20}}
```

```json
{"mode":"measures","measures":["M7:Нура","M8:Нура","M10:Нура","M12","M5:Сарыарка"]}
```

`green` также принимает `greening`, `utilities` принимает `services`. `/score` возвращает `engine` напрямую с `score`, `plan`, `sectors`, `reference` и расчётами по районам; `/simulate` возвращает объект с `meta`, `input`, `engine`, `agents`, `final_report`, `guardrails`. Не смешивайте `cost_total` с суммой лимитов `allocated_total`. HTTP 422 `invalid_plan` содержит `score: null` и причины. `POST /validate` проверяет также возможность выбрать пять мер при заданных лимитах. `GET /optimal?mode=allocation` показывает распределение лимитов, позволяющее купить общий оптимум.

API слушает `127.0.0.1:8000`; токен задаётся `AKIM_API_TOKEN` или `--api-token`, CORS включается только через `--cors-origin`, тело ограничено 1 МБ. CLI `--json` пишет только отчёт в stdout, предупреждения — в stderr. `.env` игнорируется Git.

## Проверка

`python -m pytest -q tests` проверяет опорные значения, независимый перебор на сокращённом каталоге, лимиты, несовместимости, API, офлайн-агентов, JSON Schema и fallback на локальном HTTP-моке. Для реальной калибровки понадобятся измеренные расходы, сроки, география и обращения жителей; игровая модель не предсказывает фактический эффект бюджета.
